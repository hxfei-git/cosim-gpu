# cosim-gpu 低风险分阶段学习路线

## 学习目标

用户当前是 BSP 工程师，已经具备 MMU、cache、ARM 和中断等基础知识，对 QEMU
也有一定了解。本路线的目标不是从通用计算机基础重新开始，而是复用这些经验，逐步
转型为能够独立阅读、调试和修改 GPU 驱动及其上下游软件栈的工程师。

预期形成以下能力：

- 从 PCI 枚举和驱动 probe 跟踪到 KFD、ROCm 与 GPU agent 可用。
- 解释 GPUVM、GART、PASID/VMID、queue、doorbell、AQL dispatch、completion
  signal、IH 和 MSI-X 之间的关系。
- 区分 Runtime、Driver、Firmware interface、GPU model 与 cosim transport 的职责
  和故障边界。
- 使用源码、运行日志和 artifact 证据定位初始化、地址转换、提交、执行与完成问题。
- 在已有稳定基线上增加受控观测，最终进行可回退、可对照的单变量驱动或模型实验。

HIP 算子通过只是学习载体，不是最终目标；完成路线需要既能解释机制，也能根据证据
定位问题，并在明确边界内修改实现。

## 总体策略

目标不是重新设计当前平台，而是先把已经跑通的平台当作一台“可观察的 AMD GPU”
使用：

```text
先建立项目结构与整体架构认知
→ 用一次 HIP 执行验证端到端数据流
→ 看懂初始化
→ 看懂内存与地址
→ 跟踪单个 AQL Packet
→ 看懂完成与中断
→ 增加受控观测点
→ 最后才修改模型
```

风险边界：

| 等级        | 阶段         | 对平台的影响                               |
| ----------- | ------------ | ------------------------------------------ |
| A：只观察   | Phase 1～6   | 不修改 QEMU、gem5、Guest 或 ROCm 二进制    |
| B：增加观测 | Phase 7      | 只增加默认关闭的日志、事件门和离线解析工具 |
| C：行为实验 | Phase 8 以后 | 一次只改一个变量，必须能回退并通过前后对照 |

每完成一个 Phase 就暂停。下一阶段开始前，Codex 再根据上一阶段的实际证据生成一份
较短的实施计划，而不是现在一次性设计所有细节。

## Phase 1：建立项目结构与整体架构认知

目标是建立当前项目的全局心智模型：既知道代码和产物放在哪里，也能说明运行时
模块如何连接、一次任务的数据如何往返。暂不深入 GPU 内部实现和源码函数。

### 仓库结构与正式入口

- 理解顶层仓库和两个 submodule 的边界：`gem5/` 提供模拟器与 GPU 模型，
  `gem5-resources/` 提供 Guest 镜像配方、内核和 workload 资源。
- 能说明 `configs/cosim/`、`scripts/`、`tests/`、`docs/`、`.local/` 和
  `artifacts/` 的用途，并区分以下对象：
  - Git 跟踪的源码、脚本和 lockfile；
  - submodule 中的独立源码历史；
  - 锁定的 QEMU、gem5 binary 和 Guest raw image；
  - 带 run ID 的临时资源、Guest overlay 和验收证据。
- 只通过现有 wrapper 查看 preflight、构建状态、启动、测试和清理流程；能找到每项
  操作的正式入口，但本阶段不另建命令体系。

### 运行时拓扑与职责

```text
WSL/Linux Host
├── cosim wrapper：创建 run、归档证据并按 manifest 清理
├── QEMU/KVM：执行 Guest CPU 和 Guest Linux
│   └── HIP → ROCm/ROCr → KFD/amdgpu
├── Docker：运行 gem5 GPU 模型
│   └── vfio-user endpoint → GPUVM/queue/dispatch/CU/interrupt 模型
├── vfio-user socket：PCI config、MMIO、doorbell 和 IRQ
├── Guest RAM / VRAM shared memory：queue、buffer、page table 和结果数据
└── artifacts：保存一次运行的输入身份、日志、判定和清理证据
```

需要能解释：QEMU 是 vfio-user client，gem5 是 server；amdgpu/KFD/ROCm 在 Guest
中运行；Guest CPU 由 KVM 执行，gem5 不运行第二个 Linux kernel；vfio-user socket
负责控制和通知，共享内存承载 bulk data，二者不能混为同一数据通道。

### 模块间的粗粒度数据流

本阶段只跟踪模块和数据类型，不展开寄存器、页表字段、packet 字段或源码函数：

| 路径       | 需要建立的全局认识                                                                 |
| ---------- | ---------------------------------------------------------------------------------- |
| 启动初始化 | wrapper 创建资源，gem5 发布 PCI endpoint，QEMU 启动 Guest，amdgpu/KFD/ROCm 就绪    |
| 命令提交   | HIP/ROCr 写 queue 并敲 doorbell，QEMU 经 vfio-user 通知 gem5，模型调度 GPU 工作    |
| 内存数据   | Guest RAM 与 VRAM shared memory 保存 queue、page table、输入、输出和 completion    |
| 完成返回   | gem5 完成 kernel 并更新 signal，Guest 通过 polling 或 IH/MSI-X 路径观察完成        |
| 证据与资源 | run ID 关联 manifest、日志、`gem5-evidence.tsv`、`verdict.json` 和精确清理结果 |

### 学习任务与产物

1. 先对照外部仓库的 `第一阶段导读.md` 和 `从主机到计算设备.md` 第一遍，提取
   Host/Runtime/Driver/Firmware/Hardware 通用职责；将其映射到当前 cosim，而不是
   直接复制 RDNA 3 硬件细节。
2. 阅读目录、wrapper `--help` 和既有 PASS artifact，不启动新会话就完成静态模块图。
3. 从一个既有 `vector_add` artifact 反向定位输入、Guest 输出、QEMU/gem5 日志、GPU
   执行事件、最终 verdict 和 cleanup 证据。
4. 再通过正式 wrapper 观察一次完整的新会话，把实际进程、资源名和日志对应到模块图；
   不为补充知识点修改 QEMU、gem5、Guest 或 Host 配置。
5. 形成一份简短的 Phase 1 学习记录，包含：
   - 一张仓库目录与入口图；
   - 一张运行时架构图；
   - 启动、命令、内存、完成、证据五条粗粒度数据流；
   - 一页命令与 artifact 速查；
   - `[REAL AMD]`、`[GEM5]`、`[COSIM]` 边界说明。

### 阶段边界

- 不跟踪 amdgpu 具体初始化函数；留到 Phase 3。
- 不分析 GPU 页表层级、PTE 或 TLB；留到 Phase 4。
- 不解析单个 AQL packet、queue index 或 doorbell 身份；留到 Phase 5。
- 不分析 IH cookie、MSI-X 时序或唤醒细节；留到 Phase 6。

完成标准：用户能画出仓库结构和运行时架构，解释一次 `vector_add` 如何从 Guest
到达 gem5 并返回结果，说明 socket、Guest RAM 与 VRAM 三类通道的区别；还能根据
进程、文件、日志或 artifact 判断其所属层、用途和 `[REAL AMD]`/`[GEM5]`/
`[COSIM]` 边界。

## Phase 2：把一次 HIP 执行当作黑盒看懂

在 Phase 1 的全局架构和粗粒度数据流上，使用最简单的单 GPU `vector_add` 验证
哪些节点在一次真实运行中确实发生。先看完整结果和证据闭环，不急着钻源码。

- 先使用 polling 模式运行一个全新会话。
- 再使用 interrupt 模式运行同一程序。
- 从 artifact 中确认：
  - Guest 编译的是预期源码和 `gfx942` code object。
  - HIP 程序输出 `[PASS]`。
  - gem5 记录 kernel launch、workgroup dispatch/complete 和 kernel complete。
  - 会话资源被正确清理。
- 生成一条粗粒度 timeline：

```text
Guest 启动
→ amdgpu/KFD/ROCm 就绪
→ HIP 程序启动
→ kernel launch
→ workgroup 执行
→ completion
→ 结果校验
```

完成标准：用户知道“程序成功”与“GPU 模型确实执行”是两份不同证据。

## Phase 3：启动初始化主线

利用用户已有的 PCIe、驱动和中断经验，从熟悉领域进入 GPU。

跟踪：

```text
PCI 枚举
→ BAR/ROM/discovery
→ amdgpu_pci_probe
→ IP block 初始化
→ GART/GPUVM
→ GFX/SDMA/IH ring
→ KFD device/topology
→ ROCr 枚举 gfx942
```

要求：

- 优先解析现有 `phase3-driver-002` 和启动日志，缺少证据时才运行新会话。
- 获取与 Guest DKMS 包一致的 amdgpu/KFD 源码用于阅读，不替换现有驱动。
- 每个节点标注：
  - `[REAL AMD]`：真实驱动行为。
  - `[GEM5]`：模型实现。
  - `[COSIM]`：vfio-user、synthetic PCI 或 workaround。
- 生成初始化 timeline、关键函数表和首个失败边界表。

完成标准：能从 PCI probe 一直解释到 `/dev/kfd`、render node 和 `gfx942` agent
出现。

## Phase 4：内存与地址转换

把已有 MMU/cache 知识映射到 GPU 内存体系。

学习顺序：

```text
PCI BAR
→ Guest RAM / VRAM shared memory
→ GTT/GART
→ GPU virtual address
→ VMID/PASID
→ page table / TLB
→ CU memory request
```

重点产物：

- CPU VA、Guest PA、GPU VA、VRAM offset、共享内存 offset 的对照表。
- 一次 HIP allocation 与 kernel buffer 的地址流。
- GPUVM fault 的日志识别方法。
- 真实硬件、gem5 简化模型和 cosim shared-memory workaround 的区别。

本阶段仍不修改 Guest 或 gem5 行为。

## Phase 5：单个 Packet Dispatch 主线

只跟踪 `vector_add` 中一个明确的 kernel dispatch。

源码基准：

- CLR：[`rocm-7.0.0`](https://github.com/ROCm/clr/releases/tag/rocm-7.0.0)，
  提交 `a3e329ad8a92d94bb8cdd431ab8e3ccb275a0102`。
- ROCr：[`rocm-7.0.0`](https://github.com/ROCm/ROCR-Runtime/releases/tag/rocm-7.0.0)，
  提交 `737ba1dcdfa980949e21eaaf03225c4e1e5c7a0b`。

源码只放入被 Git 忽略的本地源码区，先阅读和建立符号映射，不替换 Guest 中已验证
的 ROCm 二进制。

跟踪链路：

```text
HIP kernel launch
→ CLR/ROCr 构造 AQL packet
→ queue write index
→ release publish
→ doorbell
→ KFD/amdgpu queue、PASID/VMID/MQD
→ vfio-user BAR2 write
→ HSAPacketProcessor
→ GPUCommandProc
→ GPUDisp/CU
→ workgroup complete
```

产出一张“Packet 身份卡”，记录 kernel、grid、workgroup、queue、doorbell、
dispatch ID、CU 和关键 tick，避免在几十万行日志中盲目搜索。

完成标准：同一个 Packet 能在 HIP、ROCr、Driver 边界和 gem5 中建立有证据的对应
关系。

## Phase 6：完成、Fence 与中断

对比同一个 `vector_add` 的两条完成路径：

```text
Polling：
completion signal 更新
→ ROCr 轮询观察
→ hipStreamSynchronize 返回

Interrupt：
completion signal 更新
→ IH entry
→ IH ring write pointer
→ MSI-X
→ Guest amdgpu/KFD
→ ROCr 被唤醒
```

结合已有 interrupt artifact，确认 signal、IH cookie、write pointer、MSI-X vector
和 Guest 返回之间的顺序。

完成标准：用户能说明“kernel 已完成”“signal 已更新”“CPU 被中断唤醒”为什么是
三个不同事件。

## Phase 7：安全增加观测和暂停能力

只有完成前六阶段后才开始修改工具或模型。

优先顺序：

1. 先用离线解析器处理既有日志。
2. 再使用现有 gem5 debug flags 和 QEMU trace。
3. 证据仍不足时，才在 gem5 增加默认关闭、无状态副作用的日志点。
4. 建立事件门：在 packet fetch、doorbell、dispatch 或 completion 边界受控等待和
   继续。
5. 每个新增观测点必须带 run ID、queue/dispatch 身份和源代码位置。

当前平台没有经过验证的 QEMU/KVM、Guest RAM、VRAM、vfio-user 与 gem5 同步
checkpoint，因此本阶段的“暂停”定义为事件边界暂停，不承诺任意 tick 的全系统
保存/恢复。真正的同步 checkpoint 作为后续研究项目。

完成标准：关闭调试选项时，原 baseline 行为与证据不变。

## Phase 8：单变量修改与重放

修改顺序从低风险到高风险：

1. `HSA_ENABLE_INTERRUPT`。
2. workgroup/grid 大小。
3. `--num-cus`。
4. gem5 调试开关。
5. 一个明确的模型 latency 或 queue 参数。
6. 最后才考虑 packet、GPUVM、cache 或调度行为。

每次实验固定为：

```text
baseline run
→ 只改一个变量
→ experiment run
→ 自动生成 timeline diff
→ 结果与状态转换对比
→ regression
→ 保留或自动回退
```

任何 gem5 修改都在独立实验分支中完成；先提交 submodule，再更新顶层指针。不得同时
修改 QEMU、Guest、ROCm 和 gem5 来解释一个现象。

## Phase 9：高级专题 Labs

在两条主线稳定后逐项展开：

- PM4 packet 与 ring。
- SDMA copy 与 fence。
- GPUVM fault 和恢复边界。
- cache/TLB 行为。
- queue/doorbell 调度。
- IH/MSI-X 异常。
- firmware、PSP、SMU 等真实硬件边界与模型缺失。
- gem5 调度、CU 和内存模型。

每个 Lab 固定包含：原理、数据流、源码函数、运行方式、调试方法、正常现象、单变量
修改点，以及 `[REAL AMD]`/`[GEM5]`/`[COSIM]` 分类。
