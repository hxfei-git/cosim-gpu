# cosim-gpu 低风险分阶段学习路线

## 总体策略

目标不是重新设计当前平台，而是先把已经跑通的平台当作一台“可观察的 AMD GPU”
使用：

```text
先会运行和定位
→ 看懂初始化
→ 看懂内存与地址
→ 跟踪单个 AQL Packet
→ 看懂完成与中断
→ 增加受控观测点
→ 最后才修改模型
```

风险边界：

| 等级 | 阶段 | 对平台的影响 |
|---|---|---|
| A：只观察 | Phase 1～6 | 不修改 QEMU、gem5、Guest 或 ROCm 二进制 |
| B：增加观测 | Phase 7 | 只增加默认关闭的日志、事件门和离线解析工具 |
| C：行为实验 | Phase 8 以后 | 一次只改一个变量，必须能回退并通过前后对照 |

每完成一个 Phase 就暂停。下一阶段开始前，Codex 再根据上一阶段的实际证据生成一份
较短的实施计划，而不是现在一次性设计所有细节。

## 前置保护：封存当前可运行平台

这不是学习阶段，而是后续工作的安全保障。

- 将现有未提交内容按文档、代理规则和其他修改分别审查、测试和本地提交，不推送
  远端。
- 保留已验证运行基线：
  - 顶层运行基线：`b658840`。
  - gem5：`74e23aa96af321db127cf6ad1884753239181fd1`。
  - gem5 binary：`9fe63d9c...`。
  - Guest image：`2f155a82...`。
  - QEMU：`10.1.5`。
  - 既有 `phase7-v6` polling/interrupt 与 regression PASS artifacts。
- 建立本地 baseline 标签和恢复说明；实验失败时由 Codex 恢复，不要求用户手工
  修复。
- `0001-user-data-cn-mirror.patch` 的中文注释变化不会触发当前 Guest 重建，不以此
  为由重建镜像。
- 单独记录“Guest strict provenance 绑定顶层 HEAD”的问题。文档提交不应导致反复
  重建 55 GiB Guest；在后续修改模型前，再用独立任务解决该耦合。
- 不修改 `.wslconfig`、Docker/KVM 权限、QEMU、Guest image 或 Host 系统配置，
  除非 preflight 发现新的真实阻塞。

完成标准：现有二进制、镜像和 PASS 证据均可通过哈希定位，并存在无需重新下载或
重建的恢复路径。

## Phase 1：熟悉实验环境

先理解“谁运行在哪里”，暂不深入 GPU 内部源码。

### 学习内容

```text
WSL/Linux Host
├── Docker：运行 gem5
├── QEMU/KVM：运行 Guest Linux
├── vfio-user：连接 QEMU PCI 设备与 gem5
├── Guest：真实 amdgpu/KFD/ROCm/HIP
└── artifacts：保存一次运行的全部证据
```

### 具体方向

- 理解顶层仓库、两个 submodule、`.local/`、`artifacts/` 和 Guest overlay 的作用。
- 使用现有 wrapper 查看 preflight、构建状态、启动、测试和清理流程。
- 观察一次完整启动，但只回答：
  - QEMU 和 gem5 分别负责什么？
  - PCI GPU 是谁提供的？
  - amdgpu 在哪里运行？
  - HIP 程序在哪里编译和执行？
  - `qemu.log`、`gem5.log`、`gem5-evidence.tsv` 分别证明什么？
- 整理一张简化架构图和一页命令速查，不要求阅读大篇架构文档。

完成标准：用户能根据一个进程、文件或日志判断它属于 Host、QEMU Guest、gem5
还是 cosim 编排层。

## Phase 2：把一次 HIP 执行当作黑盒看懂

使用最简单的单 GPU `vector_add`，先看完整结果，不急着钻源码。

- 先使用 polling 模式运行一个全新会话。
- 再使用 interrupt 模式运行同一程序。
- 从 artifact 中确认：
  - Guest 编译的是预期源码和 `gfx942` code object。
  - HIP 程序输出 `[PASS]`。
  - gem5 记录 kernel launch、workgroup dispatch/complete 和 kernel complete。
  - 会话资源被正确清理。
- 生成一条粗粒度 timeline：

```text
Guest 启动
→ amdgpu/KFD/ROCm 就绪
→ HIP 程序启动
→ kernel launch
→ workgroup 执行
→ completion
→ 结果校验
```

完成标准：用户知道“程序成功”与“GPU 模型确实执行”是两份不同证据。

## Phase 3：启动初始化主线

利用用户已有的 PCIe、驱动和中断经验，从熟悉领域进入 GPU。

跟踪：

```text
PCI 枚举
→ BAR/ROM/discovery
→ amdgpu_pci_probe
→ IP block 初始化
→ GART/GPUVM
→ GFX/SDMA/IH ring
→ KFD device/topology
→ ROCr 枚举 gfx942
```

要求：

- 优先解析现有 `phase3-driver-002` 和启动日志，缺少证据时才运行新会话。
- 获取与 Guest DKMS 包一致的 amdgpu/KFD 源码用于阅读，不替换现有驱动。
- 每个节点标注：
  - `[REAL AMD]`：真实驱动行为。
  - `[GEM5]`：模型实现。
  - `[COSIM]`：vfio-user、synthetic PCI 或 workaround。
- 生成初始化 timeline、关键函数表和首个失败边界表。

完成标准：能从 PCI probe 一直解释到 `/dev/kfd`、render node 和 `gfx942` agent
出现。

## Phase 4：内存与地址转换

把已有 MMU/cache 知识映射到 GPU 内存体系。

学习顺序：

```text
PCI BAR
→ Guest RAM / VRAM shared memory
→ GTT/GART
→ GPU virtual address
→ VMID/PASID
→ page table / TLB
→ CU memory request
```

重点产物：

- CPU VA、Guest PA、GPU VA、VRAM offset、共享内存 offset 的对照表。
- 一次 HIP allocation 与 kernel buffer 的地址流。
- GPUVM fault 的日志识别方法。
- 真实硬件、gem5 简化模型和 cosim shared-memory workaround 的区别。

本阶段仍不修改 Guest 或 gem5 行为。

## Phase 5：单个 Packet Dispatch 主线

只跟踪 `vector_add` 中一个明确的 kernel dispatch。

源码基准：

- CLR：[`rocm-7.0.0`](https://github.com/ROCm/clr/releases/tag/rocm-7.0.0)，
  提交 `a3e329ad8a92d94bb8cdd431ab8e3ccb275a0102`。
- ROCr：[`rocm-7.0.0`](https://github.com/ROCm/ROCR-Runtime/releases/tag/rocm-7.0.0)，
  提交 `737ba1dcdfa980949e21eaaf03225c4e1e5c7a0b`。

源码只放入被 Git 忽略的本地源码区，先阅读和建立符号映射，不替换 Guest 中已验证
的 ROCm 二进制。

跟踪链路：

```text
HIP kernel launch
→ CLR/ROCr 构造 AQL packet
→ queue write index
→ release publish
→ doorbell
→ KFD/amdgpu queue、PASID/VMID/MQD
→ vfio-user BAR2 write
→ HSAPacketProcessor
→ GPUCommandProc
→ GPUDisp/CU
→ workgroup complete
```

产出一张“Packet 身份卡”，记录 kernel、grid、workgroup、queue、doorbell、
dispatch ID、CU 和关键 tick，避免在几十万行日志中盲目搜索。

完成标准：同一个 Packet 能在 HIP、ROCr、Driver 边界和 gem5 中建立有证据的对应
关系。

## Phase 6：完成、Fence 与中断

对比同一个 `vector_add` 的两条完成路径：

```text
Polling：
completion signal 更新
→ ROCr 轮询观察
→ hipStreamSynchronize 返回

Interrupt：
completion signal 更新
→ IH entry
→ IH ring write pointer
→ MSI-X
→ Guest amdgpu/KFD
→ ROCr 被唤醒
```

结合已有 interrupt artifact，确认 signal、IH cookie、write pointer、MSI-X vector
和 Guest 返回之间的顺序。

完成标准：用户能说明“kernel 已完成”“signal 已更新”“CPU 被中断唤醒”为什么是
三个不同事件。

## Phase 7：安全增加观测和暂停能力

只有完成前六阶段后才开始修改工具或模型。

优先顺序：

1. 先用离线解析器处理既有日志。
2. 再使用现有 gem5 debug flags 和 QEMU trace。
3. 证据仍不足时，才在 gem5 增加默认关闭、无状态副作用的日志点。
4. 建立事件门：在 packet fetch、doorbell、dispatch 或 completion 边界受控等待和
   继续。
5. 每个新增观测点必须带 run ID、queue/dispatch 身份和源代码位置。

当前平台没有经过验证的 QEMU/KVM、Guest RAM、VRAM、vfio-user 与 gem5 同步
checkpoint，因此本阶段的“暂停”定义为事件边界暂停，不承诺任意 tick 的全系统
保存/恢复。真正的同步 checkpoint 作为后续研究项目。

完成标准：关闭调试选项时，原 baseline 行为与证据不变。

## Phase 8：单变量修改与重放

修改顺序从低风险到高风险：

1. `HSA_ENABLE_INTERRUPT`。
2. workgroup/grid 大小。
3. `--num-cus`。
4. gem5 调试开关。
5. 一个明确的模型 latency 或 queue 参数。
6. 最后才考虑 packet、GPUVM、cache 或调度行为。

每次实验固定为：

```text
baseline run
→ 只改一个变量
→ experiment run
→ 自动生成 timeline diff
→ 结果与状态转换对比
→ regression
→ 保留或自动回退
```

任何 gem5 修改都在独立实验分支中完成；先提交 submodule，再更新顶层指针。不得同时
修改 QEMU、Guest、ROCm 和 gem5 来解释一个现象。

## Phase 9：高级专题 Labs

在两条主线稳定后逐项展开：

- PM4 packet 与 ring。
- SDMA copy 与 fence。
- GPUVM fault 和恢复边界。
- cache/TLB 行为。
- queue/doorbell 调度。
- IH/MSI-X 异常。
- firmware、PSP、SMU 等真实硬件边界与模型缺失。
- gem5 调度、CU 和内存模型。

每个 Lab 固定包含：原理、数据流、源码函数、运行方式、调试方法、正常现象、单变量
修改点，以及 `[REAL AMD]`/`[GEM5]`/`[COSIM]` 分类。

## 文档收敛方式

文档不再一次性写成大而全的教材。每完成一个 Phase，只新增或更新：

- 一页阶段入口。
- 一张 timeline。
- 一张源码导航表。
- 一个可重放实验。
- 一份常见失败说明。

最终再将这些内容汇总到 `README.zh.md` 和 `docs/`，形成环境、架构、初始化、
Dispatch、调试、Labs 与已知限制的渐进式学习入口。

## 默认约束与验收

- 唯一实践对象是当前 `gfx942`/MI300X cosim，不以 RX 7800 XT、RDNA 3 或物理
  GPU 为前提。
- Phase 1～6 不改变平台架构，不重建 Guest，不替换 ROCm runtime。
- 保留现有 `cosim_preflight.sh`、`cosim_build.sh`、`cosim_launch.sh` 和
  `run_cosim_tests.sh` 作为唯一正式入口。
- 后续若增加学习命令，只能包装现有入口，不能另建一套启动和构建体系。
- Codex 负责运行、采集、解析、诊断和回退；用户只负责理解当前阶段、提出问题和
  决定何时进入下一阶段。
- 不推送远端；不修改 WSL/Host 配置。
