### 0.3 我的学习目标

我不准备把 RX 7800 XT、RDNA 3 或 GFX11 作为后续实验主线，而是直接使用当前
`gfx942`/MI300X cosim 平台作为实践对象。我的目标不是只了解抽象架构，也不是只把
测试运行到 `[PASS]`，而是把这个平台当作一台能够观察和修改的 AMD GPU。

首先需要贯通两条主线：

1. **启动初始化主线**：从 PCI 枚举、BAR/MMIO、ROM/discovery 和
   `amdgpu_pci_probe` 开始，继续观察 IP block、GART/GPUVM、ring、SDMA、IH、
   GFX 与 KFD 初始化，直到 ROCr/HIP 枚举出 `gfx942` agent。
2. **Packet dispatch 主线**：从一个简单 HIP kernel 出发，跟踪 CLR/ROCr 构造
   AQL packet、KFD/amdgpu 建立 queue 和地址空间、doorbell 经 vfio-user 到达
   gem5，再观察 packet processor、command processor、dispatcher/CU 执行以及
   completion signal、polling 或 IH/MSI-X 返回结果。

在此基础上，我希望逐步做到：

- 能把运行现象对应到真实的 amdgpu/KFD、CLR/ROCr 和 gem5 源码及关键函数。
- 能画出初始化、地址转换、Packet dispatch 和完成路径的实际 timeline。
- 能明确区分真实 AMD 软件行为、gem5 模拟行为和 cosim-gpu 特有实现。
- 能在关键事件处暂停观察、增加有身份信息的日志，并重放同一个实验。
- 能一次只修改一个配置或模型变量，通过 baseline/experiment 对照理解其影响。
- 最终具备独立阅读 GPU Driver、分析 GPU 执行链路和开展小型硬件模型实验的能力。

## 1. 这份路线怎么使用

这是一份长期学习导航，不是自动执行清单。学习节奏由用户控制，任何阶段都不会
自动开始，也不会因为上一阶段完成而自动进入下一阶段。

推荐使用方式：

1. 每次只选择一个 Phase 中的一个小节。
2. 开始前明确本次是只读观察、运行实验，还是允许修改代码。
3. Codex 只完成本次明确指定的范围，整理证据并解释关键现象，然后暂停。
4. 用户可以继续提问、重复实验或回到前面的内容；理解后再主动指定下一小节。
5. 涉及构建、Guest、gem5 模型或运行合同的修改前，必须先说明影响、验证方法和
   回退路径。

例如，第一次可以这样开始：

```text
请开始 docs/学习路线.md 的 Phase 1.1，只帮助我熟悉仓库结构。
本次不要构建、启动或修改文件，解释完成后暂停。
```

## 2. 学习目标与边界

本路线只以仓库当前锁定的 `gfx942`/MI300X cosim 为实践对象，不以 RX 7800 XT、
RDNA 3、GFX11 或物理 AMD GPU 为前提。

平台的定位是：

> 把它当作一台“可暂停、可加日志、可修改硬件模型”的 AMD GPU，使用真实的
> amdgpu/KFD/ROCm 软件栈观察启动初始化和 Packet dispatch，再逐步进行可重放的
> 单变量实验。

这里的“真实”与“模拟”必须始终分开：

- `[REAL AMD]`：Guest 中真实运行的 Linux amdgpu/KFD、ROCm、CLR/ROCr 及其 ABI。
- `[GEM5]`：gem5 对 GPU 设备、命令处理、CU、内存和时序的建模。
- `[COSIM]`：vfio-user、synthetic PCI function、共享内存、驱动参数及 workaround。

本路线不会把 `[GEM5]` 或 `[COSIM]` 的现象直接宣称为物理 MI300X 的完整行为。

## 4. Phase 1：熟悉实验环境

目标是先理解“谁运行在哪里”，不深入 GPU 内部实现，也不修改平台。

### 1.1 仓库结构

逐个理解以下目录的职责和所有权：

- `gem5/`：模拟器与 MI300X GPU 模型 submodule。
- `gem5-resources/`：Guest 镜像配方、内核和资源 submodule。
- `scripts/`：唯一受支持的检查、构建、启动、测试和清理入口。
- `tests/`：HIP workload、Guest runner 与合同测试。
- `configs/`：版本锁和模拟配置。
- `.local/`：被 Git 忽略的本机构建工具与元数据。
- `artifacts/`：被 Git 忽略的运行日志、manifest、verdict 和诊断证据。

### 1.2 运行组件

建立下面这张最小心智模型：

```text
WSL/Linux Host
├── Docker container：运行 gem5 GPU 模型
├── QEMU + KVM：运行 x86 Guest Linux
├── vfio-user socket：传输 PCI config、BAR/MMIO、doorbell 和 MSI-X
├── Guest Linux：运行真实 amdgpu/KFD/ROCm/HIP
└── artifacts：保存一次会话的完整证据
```

### 1.3 构建产物与版本锁

理解 QEMU、gem5、m5、Guest image、Guest kernel 和 lock file 之间的关系。只读取
`cosim_build.sh status` 与已有 provenance，不重新构建。

### 1.4 一次运行的生命周期

理解 run ID、Guest qcow2 overlay、Unix socket、Docker container、Guest RAM、
VRAM shared memory、manifest 和 cleanup 的创建及销毁顺序。

### 1.5 Phase 1 完成参考

能够回答以下问题即可，不需要背诵源码：

- QEMU 与 gem5 分别模拟什么？
- PCI GPU function 是谁提供给 Guest 的？
- amdgpu、KFD、ROCm 和 HIP 分别在哪里运行？
- `qemu.log`、`gem5.log`、`gem5-evidence.tsv` 各能证明什么？
- 为什么每个正式测试都应使用全新会话？

## 5. Phase 2：把一次 HIP 执行当作黑盒看懂

目标是先看完整结果，再逐层拆开。

1. 先阅读已有 `vector_add` polling artifact，不立即启动新会话。
2. 识别 Guest program identity、编译结果、`[PASS]` 和 cleanup 证据。
3. 识别 gem5 的 kernel launch、workgroup dispatch/complete、kernel complete。
4. 用户明确要求后，再运行一个全新的 polling 会话。
5. 最后用同一程序观察 interrupt 模式，暂不解释中断内部细节。

本阶段形成下面这条粗粒度 timeline：

```text
Guest 启动
→ amdgpu/KFD/ROCm 就绪
→ HIP 程序启动
→ kernel launch
→ workgroup 执行
→ completion
→ Guest 校验结果
```

完成参考：能够区分“HIP 程序返回正确结果”和“gem5 中确实发生 GPU execution”
这两类证据。

## 6. Phase 3：启动初始化主线

这一阶段优先利用已有 PCIe、Driver 和中断知识，从熟悉领域进入 GPU。

```text
PCI 枚举
→ BAR / ROM / discovery
→ amdgpu_pci_probe
→ IP block 初始化
→ GART / GPUVM
→ GFX / SDMA / IH ring
→ KFD device / topology
→ ROCr 枚举 gfx942 agent
```

学习顺序：

1. 先读取已有 `phase3-driver-002` artifact，建立日志锚点。
2. 将每个状态转换映射到 amdgpu/KFD 关键函数。
3. 标记真实驱动动作、gem5 寄存器/设备响应和 cosim workaround。
4. 只有既有证据不足时，才由用户决定是否运行新的启动诊断会话。
5. 最终整理初始化 timeline 和“第一个失败组件”诊断表。

完成参考：能够从 PCI probe 解释到 `/dev/kfd`、DRM render node 和 `gfx942`
agent 出现。

## 7. Phase 4：内存与地址转换

把 CPU MMU 知识映射到 GPU 内存体系：

```text
PCI BAR
→ Guest RAM / VRAM shared memory
→ GTT / GART
→ GPU virtual address
→ PASID / VMID
→ GPU page table / TLB
→ CU memory request
```

本阶段逐步建立：

- CPU VA、Guest PA、GPU VA、VRAM offset 和 shared-memory offset 对照表。
- 一次 HIP allocation 到 kernel buffer access 的地址路径。
- GPUVM fault 的日志特征与首个错误边界。
- 真实硬件内存管理、gem5 简化模型和 cosim shared-memory 实现的区别。

本阶段仍不修改 Guest 或 gem5 行为。

## 8. Phase 5：跟踪一个 Packet Dispatch

只跟踪 `vector_add` 中一个身份明确的 kernel dispatch，不同时研究多个 workload。

匹配 Guest ROCm 7.0.0 的源码基准：

- CLR `a3e329ad8a92d94bb8cdd431ab8e3ccb275a0102`。
- ROCr `737ba1dcdfa980949e21eaaf03225c4e1e5c7a0b`。
- Guest 安装的 amdgpu DKMS 对应源码。

这些源码先放在被 Git 忽略的本地源码区，只用于阅读和符号映射，不替换 Guest
中已经验证的 ROCm 或 Driver binary。

```text
HIP kernel launch
→ CLR / ROCr 构造 AQL packet
→ queue write index 与 release publish
→ doorbell
→ KFD / amdgpu queue、PASID、VMID、MQD
→ vfio-user BAR2 write
→ HSAPacketProcessor
→ GPUCommandProc
→ GPUDisp / CU
→ workgroup complete
```

本阶段最终形成一张 Packet 身份卡，记录 kernel、grid、workgroup、queue、
doorbell、dispatch ID、CU、关键 tick、源码函数和日志行号。

完成参考：同一个 Packet 能在 HIP、ROCr、Driver 边界和 gem5 中建立有证据的
对应关系。

## 9. Phase 6：完成、Fence 与中断

使用同一个 `vector_add` 对比两条完成路径。

```text
Polling：
completion signal 更新
→ ROCr 轮询观察
→ hipStreamSynchronize 返回

Interrupt：
completion signal 更新
→ IH entry / IH ring write pointer
→ MSI-X
→ Guest amdgpu/KFD
→ ROCr 被唤醒
```

重点区分：kernel 执行完成、completion signal 更新、CPU 被中断唤醒是三个不同
事件。已有 interrupt artifact 可以先用于学习，用户决定后再进行新对照运行。

## 10. Phase 7：安全增加观测与暂停能力

完成前六阶段后，才考虑修改工具或模型。顺序固定为：

1. 先对既有日志做离线解析。
2. 再使用现有 gem5 debug flags 和 QEMU trace。
3. 证据仍不足时，增加默认关闭且无状态副作用的日志点。
4. 最后增加 packet fetch、doorbell、dispatch 或 completion 边界的受控等待点。

当前平台没有经过验证的 QEMU/KVM、Guest RAM、VRAM、vfio-user 与 gem5 同步
checkpoint。因此这里的“暂停”先定义为事件边界暂停，不承诺任意 tick 的全系统
保存和恢复。完整同步 checkpoint 是后续独立研究项目。

关闭新增调试功能时，原 baseline 的行为和证据必须保持不变。

## 11. Phase 8：单变量修改与重放

修改顺序从低风险到高风险：

1. polling 与 interrupt 模式。
2. workgroup/grid 大小。
3. `--num-cus`。
4. gem5 debug flag。
5. 一个明确的 latency、queue 或 cache 参数。
6. 最后才考虑改变 packet、GPUVM、cache 或调度语义。

每次实验只使用下面的闭环：

```text
baseline run
→ 只修改一个变量
→ experiment run
→ timeline diff
→ 结果与状态转换对比
→ regression
→ 保留修改或回退
```

任何 gem5 修改都必须位于独立实验分支；先提交 submodule，再更新顶层 gitlink。
不得同时修改 QEMU、Guest、ROCm 和 gem5 来解释一个现象。
