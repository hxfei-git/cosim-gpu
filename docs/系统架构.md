# 协同仿真系统架构

本文描述当前仓库的实现范围，实测边界另行标注；即使 experimental code 尚无
accepted runtime evidence，也会明确标识。全文始终区分真实 AMD 行为、gem5 模型
行为与协同仿真兼容代码。可运行实验见[学习实验](学习实验.md)，构建和诊断命令见
[调试参考](调试参考.md)。

## 1. 阅读约定与证据 baseline

全文使用以下标签：

- `[REAL AMD]` 表示 Linux amdgpu/KFD 与 ROCm 的设计。匹配的 Guest 软件包已
  固定，但其完整源码树没有 vendored 到本仓库；canonical upstream 路径和函数名
  只是源码导航锚点，不代表本地行号。
- `[GEM5]` 表示 `gem5/` submodule 中的实现。
- `[COSIM]` 表示本仓库的 QEMU/KVM、vfio-user、共享内存集成、启动策略或
  兼容性 workaround。

当前代码默认创建一个 synthetic `1002:74a0` endpoint、16 GiB VRAM、8 GiB
Guest RAM 和 40 个建模 CU。`artifacts/amd-gpu-learning-env/tests/` 中保留的
runtime 证据已证明：

| 证据                                                      | 已证明现象                                                                                    |
| --------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| `phase3-driver-002/phase3-verdict.json`                 | PCI endpoint 与 BAR、amdgpu 绑定、`/dev/kfd`、DRM render node、ROCm 7.0 和 `gfx942` agent |
| `phase4-baseline-vector-add-i0/dispatch-verdict.json`   | AQL task 2、grid 4352、workgroup size 256、workgroup 0–16 以及 gem5 kernel completion        |
| `phase4-interrupt-vector-add-i1/interrupt-verdict.json` | signal 1→0、IH cookie/write-pointer 更新，以及同一 gem5 tick 的 vfio-user IRQ vector 0       |

这些 artifact 只证明对应 configuration 与 binary provenance，不能证明 timing
精度，也不能证明物理 MI300X 上未经测量的行为。

## 2. 系统边界

### 2.1 进程拓扑

```text
Host Linux / WSL2
  QEMU 10.1.5，Q35 + KVM
    Guest Linux 6.8.0-79
      HIP application
      ROCm userspace / ROCr
      KFD + amdgpu
    QEMU vfio-user-pci client
              |
              | vfio-user Unix socket：config、MMIO、doorbell、IRQ
              v
  Docker container
    gem5 VEGA_X86，StubWorkload
      MI300XVfioUser
      AMDGPUDevice / AMDGPUVM
      PM4PacketProcessor / SDMAEngine / AMDGPUInterruptHandler
      HSAPacketProcessor / HWScheduler
      GPUCommandProcessor / GPUDispatcher / Shader / CUs
      GPU_VIPER Ruby memory hierarchy

Shared mappings
  run-scoped Guest RAM shmem  <-> QEMU memory-backend-file / gem5 backstore
  run-scoped VRAM shmem       <-> BAR0 / gem5 device-memory backstore
```

`[COSIM]` QEMU 通过 KVM 执行 Guest CPU 与 kernel。gem5 不会再启动一个 Linux
kernel；它的 `StubWorkload` 只承载 GPU 侧对象。`MI300XVfioUser` 是 vfio-user
server，QEMU 内置的 `vfio-user-pci` 是 client。runtime 路径不需要项目私有的
QEMU device patch。

### 2.2 传输通道

| 通道                    | 承载内容                                                    | 实现                                                                                                                                     |
| ----------------------- | ----------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| vfio-user socket        | PCI config、BAR2 doorbell、BAR5 MMIO、reset 与 IRQ protocol | `[COSIM]` `MI300XVfioUser` + libvfio-user ↔ QEMU `vfio-user-pci`                                                                  |
| VRAM shared memory      | BAR0 字节、page table 和 device-local allocation            | `[COSIM]` 每次运行独立的 `/dev/shm/mi300x-vram-<run>`；可 mmap 的 BAR0 与 gem5 VRAM backstore                                        |
| Guest RAM shared memory | GTT/system page、queue、signal、fence 和 IH buffer          | `[COSIM]` 每次运行独立的 `/dev/shm/cosim-guest-ram-<run>`；QEMU `memory-backend-file,share=on` 与 gem5 `system.shared_backstore` |

socket 是控制与通知路径，不是 bulk-memory coherence protocol。共享文件提供字节
可见性，gem5 Ruby hierarchy 建模 GPU 侧 traffic。这一组合适合功能研究，但不等同
于物理 CPU/GPU cache coherence。

### 2.3 会话与磁盘隔离

`[COSIM]` 每次启动都有 run ID、唯一 socket/shared-memory 名、resource manifest
和 artifact directory。raw Guest image 按不可变对象管理，只作为 run-scoped
qcow2 overlay 的 backing file。清理只能依据通过校验的 manifest 执行，因而成功
或失败的 Guest 会话都不会静默修改下一次运行的基础镜像。

中断后的 fallback 还有额外 ownership 前置条件：只能使用可信、run-scoped 的
`launcher.pid` 校验 launcher process group 及其 `scripts/cosim_launch.sh` command
line，停止该精确 process group 并确认它已经退出；随后才允许把仍存在的 exact
manifest 交给 `cosim_cleanup.sh`。PID file 缺失、为 symlink、陈旧，或与已记录的
artifact directory 不匹配时必须停止并诊断，不能猜 PID，也不能使用宽泛 kill。

实现位于 [`scripts/cosim_launch.sh`](../scripts/cosim_launch.sh)、
[`scripts/cosim_lib.sh`](../scripts/cosim_lib.sh) 和
[`scripts/cosim_cleanup.sh`](../scripts/cosim_cleanup.sh)。

## 3. PCI endpoint、BAR 与 MMIO

### 3.1 实测 BAR 布局

Phase 3 Guest probe 实测得到以下精确布局：

| BAR    |    大小 | 作用                                      | Access path                                                   |
| ------ | ------: | ----------------------------------------- | ------------------------------------------------------------- |
| BAR0+1 |  16 GiB | prefetchable VRAM aperture                | mmap VRAM shared-memory fd；另有 callback fallback            |
| BAR2+3 |   2 MiB | non-prefetchable doorbell aperture        | vfio-user callback →`AMDGPUDevice::writeDoorbell`          |
| BAR4   |   8 KiB | MSI-X table 与 PBA，advertise 256 vectors | 由 libvfio-user/QEMU 处理；当前模型只 raise vector 0          |
| BAR5   | 512 KiB | GPU MMIO registers                        | vfio-user callback →`AMDGPUDevice::readMMIO`/`writeMMIO` |

`[COSIM]` endpoint 将 vendor/device/subsystem ID 设置为 `1002:74a0`，PCI class
为 `0x030000`，为 BAR0 与 BAR2 设置 64-bit type bits，并提供 expansion ROM
window。BAR 大小以 `MI300XVfioUser::BAR*_SIZE` 为准，不能从旧文档或物理板卡
datasheet 反推。

### 3.2 访问路径

```text
Guest amdgpu MMIO 或 doorbell access
  -> QEMU vfio-user-pci
  -> MI300XVfioUser::{handleMmioAccess,handleDoorbellAccess}
  -> AMDGPUDevice::{writeMMIO,writeDoorbell}
  -> NBIO / GPUVM / PM4 / SDMA / IH / HSA queue owner
```

`AMDGPUDevice::writeDoorbell` 查找已注册的 doorbell offset，并按
`QueueType` 路由到 PM4 graphics/compute、SDMA gfx/page/RLC、Compute AQL，
或 IH read-pointer update。未知 offset 会被保留为 pending doorbell；它是需要与
queue setup 关联的证据，本身不能证明 root cause。

相关模型源码：

- [`mi300x_vfio_user.cc`](../gem5/src/dev/amdgpu/mi300x_vfio_user.cc)：
  `initVfuContext`、`setupBars`、BAR callback、`sendIrqRaise`。
- [`amdgpu_device.cc`](../gem5/src/dev/amdgpu/amdgpu_device.cc)：
  `writeDoorbell`、`writeMMIO`、`setDoorbellType`、VMID/PASID map。

## 4. amdgpu 与 KFD 初始化

### 4.1 分层初始化流程

```text
Linux PCI core 枚举 1002:74a0 并分配 BAR
  -> cosim-gpu-setup.service 发布 ROM 与 discovery firmware
  -> amdgpu_pci_probe / amdgpu_device_init
  -> 选定 IP block 初始化 GMC/GART、IH、GFX 与 SDMA
  -> amdgpu 建立 DRM node 并把设备交给 KFD
  -> KFD 建立 topology、process/queue 与 doorbell interface
  -> ROCr 枚举 KFD agent
  -> HIP 看到 gfx942
```

`[REAL AMD]` 常用 driver 导航锚点：

- `drivers/gpu/drm/amd/amdgpu/amdgpu_drv.c`：`amdgpu_pci_probe`。
- `drivers/gpu/drm/amd/amdgpu/amdgpu_device.c`：`amdgpu_device_init` 与 IP
  block lifecycle。
- `drivers/gpu/drm/amd/amdgpu/amdgpu_discovery.c`：IP discovery parsing。
- `drivers/gpu/drm/amd/amdkfd/kfd_device.c` 与 `kfd_chardev.c`：KFD device
  creation 和 userspace ioctl entry。

必须按 `configs/cosim/guest.lock` 中的 DKMS 版本核对这些函数；本仓库没有 vendor
完整 driver source。

### 4.2 协同仿真策略

`[COSIM]` Guest boot 时先 blacklist amdgpu，使 systemd service 能在驱动 probe
前发布 synthetic ROM 与 `mi300_discovery` 数据。随后 service 使用以下参数加载
amdgpu：

```text
ip_block_mask=0x67 ppfeaturemask=0 dpm=0 audio=0 ras_enable=0 discovery=2
```

这会选择模型已实现的子集，并禁用依赖缺失 firmware/hardware 的 PSP、SMU、
power management、audio 与 RAS 路径。这是协同仿真 boot contract，不是物理 GPU
的推荐配置。VCN/JPEG 也不在 compute acceptance path 中。

discovery 数据报告的 topology 大于 gem5 实例化规模：Guest 实测报告
`active_cu_number 320`，默认 gem5 command 只创建 40 个 CU。driver-visible
topology 只证明 ROCm 接受 synthetic device，不能当成建模 CU 数或 performance
结论。

## 5. VRAM、GTT、GART 与 GPUVM

### 5.1 这些术语不能互换

| 术语  | 在本环境中的含义                                                                                                 |
| ----- | ---------------------------------------------------------------------------------------------------------------- |
| VRAM  | device-local allocation domain 与 BAR0 aperture；配置为 16 GiB，driver 报告约 16383 MiB usable                   |
| GTT   | 由 Guest/system RAM 支撑的 driver placement domain；Phase 3 probe 报告约 3970 MiB ready                          |
| GART  | 将 GPU-visible address 映射到 system page 的 VMID0 aperture/page table；probe 报告 512 MiB PCIe GART             |
| GPUVM | 由 VMID 选择、与 PASID 关联的 per-process GPU virtual address space；user mapping 使用 multilevel GPU page table |

GTT 描述 memory placement；GART 与 GPUVM 描述 address translation。“GTT table”
不能当成 GART 的同义词。

### 5.2 Shared backstore 与物理地址

`[COSIM]` 默认 8 GiB Guest 的 Q35 layout 留有 PCI hole：gem5 对应建模 4 GiB
以下的 2 GiB，以及 4 GiB 以上的其余内存。system-memory DMA address 必须保留
Guest physical 语义。IH ring base 与 write-pointer address 是 system DMA address，
不经过 GART translation generator。

VRAM 是另一条路径。`MI300XVfioUser::setupSharedMemory` 创建并映射 VRAM object，
通过 BAR0 暴露 fd，把 pointer 交给 `AMDGPUVM`，并把 GPU page-table walker 接到
该 mapping。gem5 device-memory backstore 使用相同的 per-GPU name。

### 5.3 VMID0 GART 与 user GPUVM

`[GEM5]` `AMDGPUVM` 记录 driver 写入的 aperture 和 page-table register。

- `GARTTranslationGen::translate` 执行 VMID0 single-level lookup：先查模型的
  `gartTable` shadow，也可以再从 shared VRAM 读取 PTE。
- `UserTranslationGen::translate` 按 user VMID 选择 page-table base，并调用 Vega
  page-table walker。PTE `system` bit 选择 system memory；device-local 结果通过
  MMHUB aperture 转换。
- `PM4PacketProcessor::mapProcess` 为 PASID 分配 VMID 并安装 process page-table
  base。doorbell 与 queue 保留后续 DMA 和 completion 所需的 VMID。
- `MMHUBTranslationGen::translate` 把 local VRAM offset 转成模型的 global VRAM
  address；这对 multi-GPU configuration 很重要。

应把 [`amdgpu_vm.cc`](../gem5/src/dev/amdgpu/amdgpu_vm.cc) 与
[`pagetable_walker.cc`](../gem5/src/arch/amdgpu/vega/pagetable_walker.cc)
结合 PM4/queue ownership 一起阅读。

### 5.4 Translation 与 coherence 边界

`[COSIM]` 以下两条兼容路径不是真实硬件语义：

1. 正常模型内存可见性不足时，page-table walker 可直接从 VRAM shared mapping
   读取 PTE。
2. GART PTE 缺失或 timing walk fault 时，可能映射到 physical address 0 以保持
   simulator 继续运行。

第二条是会丢失语义的危险 fallback。address 0 在当前模型中是有效 Guest RAM；
read 可能错误，write 可能被丢弃或破坏无关数据。每次发生都必须保留在 artifact
中，绝不能描述为 safe sink 或成功 translation。

TLB invalidate、page-walk-cache state、SQC/GL2 maintenance、Ruby traffic 与
direct shared-memory visibility 是不同机制。一个小 kernel PASS 不能证明完整的
cache-coherence 语义。

## 6. Ring、queue 与 doorbell

系统有两个相关但不同的 command plane：

| Plane                   | Producer 与 payload                                               | 模型 consumer                            |
| ----------------------- | ----------------------------------------------------------------- | ---------------------------------------- |
| Kernel/management plane | amdgpu/KFD 在 KIQ/runlist/compute management ring 中写 PM4 packet | `PM4PacketProcessor`                   |
| User compute plane      | ROCr 向 process queue 写 64-byte AQL packet                       | `HWScheduler` + `HSAPacketProcessor` |

`[REAL AMD]` KFD 创建 process queue、映射 doorbell page 并配置 MQD。ROCr 更新
AQL write index 后写 mapped doorbell，正常 dispatch fast path 不会为每个 kernel
再发一次 ioctl。

`[GEM5]` PM4 `MAP_PROCESS` 建立 PASID/VMID state；`MAP_QUEUES` 读取 MQD，
通过 `HSAPacketProcessor::setDeviceQueueDesc` 注册 queue，并关联 doorbell。
后续 user doorbell 由 `HWScheduler::write` 接收，更新 queue state 并调度 AQL
processing。`HSAPacketProcessor` 从 Guest queue DMA packet，并推进 read/dispatch
pointer。

因此“ring”必须说明 owner：PM4 ring、SDMA ring、AQL queue 与 IH ring 的 packet
format 和 completion rule 都不同。

## 7. PM4 模型

### 7.1 在 HIP 路径中的作用

PM4 对 driver 初始化、process mapping、queue creation、runlist、memory write 与
synchronization 很重要。但把 HIP kernel body 描述成 PM4 并由
`PM4PacketProcessor` 执行是不准确的：模型真正消费的 compute dispatch payload
是 AQL kernel-dispatch packet，PM4 负责准备并管理承载它的 queue。

```text
KFD/amdgpu management ring doorbell
  -> AMDGPUDevice::writeDoorbell
  -> PM4PacketProcessor::process
  -> decodeNext / decodeHeader
  -> mapProcess / mapQueues / runList / indirectBuffer / writeData /
     releaseMem / waitRegMem / queryStatus
```

正确入口是 `PM4PacketProcessor::process`；`processPkt` 属于
`HSAPacketProcessor`，不能写成 PM4 函数名。

### 7.2 建模范围

当前实现覆盖现有软件栈需要的 packet，但不是 bit-for-bit 或 timing-complete 的
MI300X command processor。unsupported packet variant 可能 warn、panic 或采用
简化 completion。queue、VMID、cache-maintenance 与 release 语义必须按 workload
验证。源码见
[`pm4_packet_processor.cc`](../gem5/src/dev/amdgpu/pm4_packet_processor.cc)
与 [`pm4_defines.hh`](../gem5/src/dev/amdgpu/pm4_defines.hh)。

## 8. SDMA 模型

`[REAL AMD]` SDMA engine 独立执行 copy/write/fill、page-table 与 synchronization
packet；queue doorbell 通知 engine write pointer 已推进。

`[GEM5]` 默认 configuration 创建 16 个 `SDMAEngine`。MMIO setup 注册 gfx/page
queue 和 doorbell offset，`processGfx`、`processPage` 或 `processRLC` 开始 decode。
已实现 handler 包括 `write`、`copy`、`indirectBuffer`、`fence`、`trap`、
`pollRegMem`、`ptePde`、`atomic` 与 `constFill`，但各 operation 都可能有限制。

SDMA access 前必须区分 raw local VRAM、MMHUB/device memory、VMID0
GART/system memory 或 user GPUVM。模型使用 `getDeviceAddress`、`getGARTAddr`
和 `translate`；靠近 SDMA 的失败不一定是 SDMA decoder bug，也可能是 queue
ownership 或 address translation。

SDMA fence packet 写入数值并推进 queue；独立的 trap packet 才会 post IH event。
“fence”和“interrupt”不是同义词。

## 9. Fence、completion signal、IH 与 MSI-X

同步存在多个层次：

- `[REAL AMD]` driver fence 表示有序 completion，可由 sequence value 与
  interrupt/wakeup path 支撑。
- `[GEM5]` PM4 `RELEASE_MEM` 与 SDMA `fence` 为各自 engine 写 completion data。
- `[GEM5]` HSA kernel completion 通过
  `GPUCommandProcessor::sendCompletionSignal` 递减 AQL completion signal；它
  不是 PM4 或 SDMA fence object。

interruptible HSA signal 的实测模型路径为：

```text
GPUCommandProcessor::updateHsaSignalData 写 signal 1 -> 0
  -> AMDGPUInterruptHandler::prepareInterruptCookie（CP_EOP、PASID/VMID）
  -> submitInterruptCookie 向 Guest IH ring 写 256-bit entry
  -> submitWritePointer 更新 Guest IH write-pointer location
  -> AMDGPUDevice::intrPost
  -> MI300XVfioUser::sendIrqRaise(0)
  -> libvfio-user / QEMU 向 Guest 注入 MSI-X
  -> amdgpu/KFD 消费 event 并唤醒 ROCr
```

Guest 消费 IH ring 后通过 IH doorbell 更新 read pointer。`[COSIM]` 当前只模拟
CP_EOP 与 TRAP_ID source。CP_EOP cookie 会把较低的模型 VMID clamp 到 driver
的 compute-VMID 范围（8–15），同时保留由真实模型 mapping 得到的 PASID。BAR4
advertise 256 vectors，但 bridge 当前只 raise vector 0。

polling (`HSA_ENABLE_INTERRUPT=0`) 能在不依赖这条 wakeup chain 的情况下证明
completion。interrupt mode (`1`) 是独立实验，必须同时出现 signal、IH write 与
MSI-X 证据，不能只有最终 `[PASS]`。

## 10. HIP 到 gem5 的端到端 dispatch

### 10.1 真实软件栈视角

```text
HIP source 编译为 gfx942
  -> HIP runtime（amdhip64）
  -> ROCr/HSA 发现 KFD agent 并创建 AQL queue
  -> KFD/amdgpu 建立 process VM、memory mapping、MQD 与 doorbell
  -> ROCr 写 kernel object、kernarg 与 64-byte AQL dispatch packet
  -> ROCr publish queue write index 并写 doorbell
  -> GPU 执行 kernel
  -> completion signal 递减
  -> polling 或 KFD event 唤醒等待的 host thread
  -> HIP copy/check result
```

KFD/amdgpu 参与 device、VM、memory 与 queue setup；正常 per-dispatch fast path
是 userspace AQL write 加 doorbell，不是每个 kernel 一次 KFD ioctl。

### 10.2 gem5/cosim 视角

```text
Guest AQL queue 与 buffer 位于 shared Guest RAM / VRAM
  -> QEMU 通过 vfio-user 转发 BAR2 doorbell
  -> AMDGPUDevice 路由 ComputeAQL doorbell
  -> HWScheduler 选择已注册 queue
  -> HSAPacketProcessor DMA 并 decode AQL packet
  -> GPUCommandProcessor::submitDispatchPkt 读取 code object 与 kernarg
  -> GPUCommandProcessor::dispatchPkt
  -> GPUDispatcher 把 workgroup 分配给 Shader/CU
  -> CU execution 与 Ruby GPU memory traffic
  -> GPUDispatcher completion
  -> GPUCommandProcessor 递减 HSA completion signal
  -> polling 或 IH/MSI-X completion path
  -> Guest HIP code 观察数据并返回 PASS
```

保留的 vector trace 把精确 source SHA 与 Task 2、4352-thread grid、workgroup
size 256、全部 17 个 workgroup、HSA completion 和 kernel completion 关联起来。
两次 transient pending-invalidate launch retry 也保留在 verdict 中，没有被隐藏。
这是声明 GPU 模型真正执行所需的最低证据；只有编译成功与 Guest output 不够。

## 11. Multi-GPU 与 xGMI 边界

configuration 可以建立多个 GPU device；每个都有独立 vfio-user bridge、VRAM
mapping、shader、PM4、SDMA 与 IH object。所有 CU 接入同一 gem5 process 和共享
的 disjoint VIPER hierarchy。可选 `XGMIBridge` 支持配置 bandwidth/latency 的
ring 或 mesh routing。

这属于 `[GEM5]` experimental modeling，不是已验证的物理 xGMI fabric。正常
launcher 暴露 `--num-gpus`，但不暴露 xGMI topology 参数；已验收的 single-endpoint
baseline 也没有证明 xGMI coherence、ordering、peer-DMA 或 performance fidelity。
还要区分多个 synthetic PCI endpoint 与一个 Guest device 的 discovery topology
所暴露的多个 XCP/DRM node。

## 13. 已知限制与禁止推断项

- synthetic PCI config space、ROM、discovery data、reset 与 error behavior 不是
  物理 MI300X 行为。
- PSP、SMU、RAS、DPM、audio 与 media block 被禁用或超出范围。
- driver-visible 320 个 CU 与八个 partition/render node，不是默认模型实例化的
  40 个 CU。
- PM4、SDMA、IH source、firmware scheduling、cache maintenance、atomic 与
  page-fault recovery 均为部分实现并依赖 workload。
- direct PTE read、VMID clamp、invalidate ACK shortcut 与 address-zero fallback
  是 cosim compatibility mechanism，不是硬件 contract。
- shared-memory visibility 与 Ruby 的组合不能证明完整 heterogeneous coherence，
  当前 gem5 timing 也没有针对 MI300X performance calibration。
- multi-GPU/xGMI 代码存在，但 accepted baseline 没有证明物理 topology、
  peer-memory 或 link fidelity。
- PASS 只对 runner 保存的精确 source、binary、environment、log、cleanup 与
  verdict 有效。artifact-first acceptance contract 见[调试参考](调试参考.md)。
