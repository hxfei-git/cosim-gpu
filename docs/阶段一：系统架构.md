# 阶段一：系统架构

这篇文档只解决三个问题：

1. **项目里的代码、二进制、临时资源和证据分别放在哪里？**
2. **QEMU、Guest Linux、gem5 和 vfio-user 在运行时怎样连接？**
3. **一次 `vector_add` 怎样到达 GPU 模型，又怎样带着结果和证据回来？**

Phase 1 先建立项目的整体结构认知：看到一个进程、路径或日志时，能够判断它位于
哪一层、负责哪一段、下一步应检查哪里。寄存器字段、页表格式、单个 AQL Packet 和
中断时序会在后续阶段逐层展开。

开始前先记住三句话：

> 1. KVM 执行 Guest CPU，gem5 只模拟 GPU 后端，不运行第二个 Linux kernel。
> 2. vfio-user socket 主要传递设备控制与通知，共享内存承载大块 RAM/VRAM 数据。
> 3. “程序 PASS”“GPU 模型确实执行”“资源正确清理”是三份不同证据。

## 1. 从熟悉的向量加法出发

### 1.1 算法没变，任务表达方式变了

在 CPU 上，向量加法可以直接写成循环：

```c
for (i = 0; i < n; i++)
    C[i] = A[i] + B[i];
```

GPU 版本并不是 CPU 逐条发送“读 A、读 B、相加、写 C”。应用只提出一次计算请求，
Runtime 把请求整理成设备能理解的任务，GPU 再自行取任务、取指和执行。

```text
应用：我需要计算 C = A + B
  │
  ▼
Runtime：把“运行哪个 Kernel、参数在哪、规模多大”写入 Queue
  │
  ├── 写 Queue      —— 放入任务正文
  └── 写 Doorbell   —— 通知设备“有新任务”
                         │
                         ▼
GPU 命令前端：取得任务，建立一次 Dispatch
                         │
                         ▼
GPU 计算资源：执行 Kernel，写回 C，更新 Completion Signal
                         │
                         ▼
Runtime/应用：观察完成条件，读取并校验 C
```

这些对象与 BSP 中的描述符提交路径有相似之处，但含义并不完全相同：

| GPU 对象                      | 技术含义                                   | 与 BSP 经验的关系                                         |
| ----------------------------- | ------------------------------------------ | --------------------------------------------------------- |
| Queue（队列）                 | GPU 可访问的环形内存，保存待处理 Packet    | 组织形式接近 descriptor ring，但 Packet 引用可编程 Kernel |
| Doorbell（门铃）              | 映射给提交者的 MMIO 通知入口               | 作用接近 kick register，不携带 Packet 正文                |
| Dispatch（派发）              | 设备根据 Packet 建立的一次 Kernel 执行实例 | 不等于一条 DMA transaction，会展开为并行工作              |
| Completion Signal（完成信号） | Runtime 可查询或等待的同步对象             | 接近 completion flag/counter，但不等于 IRQ                |

最重要的一组区别是：

```text
Queue      = 任务放在哪里
Doorbell   = 怎样提醒设备
Dispatch   = 设备建立的一次执行
Signal     = 怎样表示执行已经完成
```

### 1.2 三类代码不要混在一起

```text
Guest CPU 侧                                      GPU 设备侧

Host 应用代码 ──► Runtime ──► Linux Driver        GPU Kernel ──► GPU 计算资源
表达 C = A + B     组织任务     建立资源和权限       定义算法       执行 load/add/store

真实硬件中还可能有 GPU Firmware：
负责安全、电源、部分 Queue 控制或恢复，不等于应用 Kernel，
也不保证出现在每次 Dispatch 的热路径。
```

这里的 GPU Kernel 是应用设备程序；Linux kernel 是 Guest 操作系统内核；GPU
Firmware 则运行在真实 GPU 的专用控制处理器或微引擎上。三者的执行位置、指令集和
生命周期都不同。

## 2. 区分三个运行域

掌握任务语言后，下一步是回答“这些参与者究竟运行在哪里”。本项目不是简单的
“Host 程序连接一颗物理 GPU”，而是外层 Host 同时承载 QEMU 和 gem5。

### 2.1 两种 Host 语境

| 本文名称     | 实际位置         | 运行内容                                                  |
| ------------ | ---------------- | --------------------------------------------------------- |
| 外层 Host    | WSL/Linux 环境   | wrapper、QEMU、Docker、Host 文件与 artifact               |
| Guest CPU 侧 | QEMU Guest 内    | HIP 应用、ROCm Runtime、Guest Linux、amdgpu/KFD           |
| GPU 模型侧   | Docker 内的 gem5 | vfio-user endpoint、GPUVM、Queue、Dispatch、CU 和完成模型 |

通用 ROCm 材料中的“Host 应用”是 GPU 编程语境下的 CPU 应用。在本项目中，它运行在
**Guest CPU 侧**，不是外层 WSL shell。

### 2.2 运行时全景图

```text
WSL/Linux 外层 Host
│
├─ cosim wrapper（运行管理）
│  ├─ 选择锁定输入
│  ├─ 创建 run ID、overlay、manifest
│  └─ 归档证据并清理本 run
│
├─ QEMU/Q35 + KVM                                      [COSIM]
│  │
│  │  KVM 执行 Guest CPU；QEMU 提供内存、磁盘、PCI、串口、9p
│  ▼
│  ┌──────────────── Guest Linux ─────────────────────┐
│  │ HIP 应用 → ROCm/HIP/ROCr → KFD/amdgpu           │ [REAL AMD]
│  └──────────────────────┬───────────────────────────┘
│                         │ Guest 发起 PCI/BAR 访问
│                         ▼
│                 QEMU vfio-user-pci client
│                         │
│                         │ Unix socket
│                         ▼
├─ Docker ─────── gem5 MI300XVfioUser server           [COSIM]
│                         │
│                         ▼
│                  gem5 GPU 行为模型                    [GEM5]
│             GPUVM / Queue / Dispatch / CU / Interrupt
│
├═ Guest RAM shared memory ══ QEMU 与 gem5 共同映射
├═ VRAM shared memory      ══ BAR0 与 GPU 模型共同使用
└─ artifacts/                 输入身份、日志、事件、判定、清理证据
```

从图中应当直接看出：

- **Guest Linux 只有一份。** 它由 QEMU/KVM 运行；gem5 里没有第二个 Guest。
- **Docker 只是 gem5 的运行容器。** Docker 本身不定义 GPU 行为。
- **QEMU 是 vfio-user client，gem5 是 server。** gem5 先发布 endpoint，QEMU
  随后连接。
- **amdgpu/KFD/ROCm 都在 Guest 中。** 被研究的驱动栈不在外层 WSL kernel 中。

当前默认单 GPU 配置为 8 GiB Guest RAM、16 GiB VRAM 和 40 个建模计算单元（CU）。Guest
软件栈把设备识别为 `gfx942` 目标；这些是当前模型配置，不是物理 MI300X
数量或性能结论。

### 2.3 用一句话记住每个模块

- **wrapper 负责运行管理。** 它不执行 CPU/GPU 指令，只负责锁定输入、创建 run、
  留证和清理。
- **QEMU/KVM 是 Guest 机器。** KVM 执行 Guest CPU，QEMU 提供虚拟平台并代理 PCI
  设备访问。
- **Guest Linux 是目标软件栈所在处。** HIP、ROCm、amdgpu/KFD 都在这里运行。
- **vfio-user 是设备边界。** 它让 QEMU 看到一个标准 PCI function，同时把访问交给
  gem5。
- **gem5 是 GPU 后端。** 它建模 GPUVM、命令处理、Dispatch、CU 与完成路径。
- **artifact 是实验记录。** 它回答“本次到底用了什么、发生了什么、为何这样判定”。

9p share 只是 runner 把测试源码和脚本暴露给 Guest 的文件共享，不是 GPU Queue、
Doorbell 或 VRAM 通道。

### 3.2 从源码到证据的流水线

```text
顶层源码 + 两个 submodule + lockfile
                 │
                 │ wrapper 构建
                 ▼
       可复用的锁定二进制/Guest image
                 │
                 │ wrapper 创建一次 run
                 ▼
 socket + shared memory + overlay + container
                 │
                 │ 运行、采集、分类、清理
                 ▼
      artifacts/<类别>/<run-id>/
```

这张图提供了一个实用判断：

- 想知道“实现在哪里”，先看顶层源码或 submodule。
- 想知道“实际跑的是哪份二进制”，看 lock、metadata 和 provenance（来源身份记录）。
- 想知道“这一轮发生了什么”，看带 run ID 的 artifact。
- 想知道“现在还有什么资源活着”，看该 run 的 manifest，而不是宽泛搜索后删除。

## 4. 用 run ID 串起一次会话

run ID 用于标识一次会话，并关联该会话创建的全部运行资源和证据。

### 4.1 用真实样本看资源命名

本文后面使用的既有样本 run ID 是：

```text
quick-vector-add-20260826-225106
```

把这个 ID 代入命名规则，可以得到该会话的资源名称：

```text
quick-vector-add-20260826-225106
│
├─ container   gem5-cosim-quick-vector-add-20260826-225106
├─ socket      /tmp/gem5-mi300x-quick-vector-add-20260826-225106.sock
├─ Guest RAM   /dev/shm/cosim-guest-ram-quick-vector-add-20260826-225106
├─ VRAM        /dev/shm/mi300x-vram-quick-vector-add-20260826-225106
├─ session     /tmp/cosim-quick-vector-add-20260826-225106.session/
│  ├─ guest-overlay.qcow2
│  └─ resources.manifest
└─ artifact    artifacts/quick/quick-vector-add-20260826-225106/
```

看到任意一个名字，都应该能反推出同一个 run ID，并找到同一会话的其他对象。
这个样本已经正常结束，因此上面的 runtime 资源现在不应继续存在；保留下来供学习的
是 artifact。

### 4.2 一次 run 的生命周期

```text
生成 run ID
   │
   ├─ 创建 manifest：本 run 拥有哪些资源
   ├─ 创建 overlay：本 run 对 Guest 磁盘的临时写入层
   └─ 创建 artifact：本 run 的实验记录目录
   │
   ▼
先启动 gem5 server
   │  等待 socket、Guest RAM、VRAM、container 就绪
   ▼
再启动 QEMU client 和 Guest Linux
   │
   ▼
加载 amdgpu/KFD，运行 HIP 算子，采集两侧证据
   │
   ▼
生成 verdict
   │
   ▼
停止本 run，按 manifest 精确清理，验证清理结果
```

三个文件对象的职责分别是：

- **overlay** 是本次 run 的 qcow2 可写层。Guest raw image 作为只读 backing，
  Guest 的磁盘修改只写入 `guest-overlay.qcow2`。
- **manifest** 记录本次 run 拥有的 container、socket、shared memory、overlay 和
  session 目录，用于精确清理和所有权校验。
- **artifact** 在临时资源清理后继续保留输入身份、日志、结构化事件和最终判定。

正常 runner 会自动停止并清理。`./scripts/cosim_cleanup.sh --run-id <id>` 默认只是
dry-run 盘点。若 launcher 仍活着，必须先验证并停止精确 process group、确认退出，
随后才允许 exact-manifest cleanup；禁止宽泛 kill 或通配删除 `/tmp`、
`/dev/shm`。

Guest 中 amdgpu 已经发生部分 `hw_init` 后，也不在同一 Guest 原地卸载或
重载驱动，更不能通过 `/dev/mem` 手工制造成功结果；结束 run 后使用全新
会话。

## 5. vfio-user socket 与两类共享内存

运行资源已经可见后，最容易混淆的问题是：既然有 socket，为什么还要两份 shared
memory？

它们承担不同职责：socket 传递 PCI 配置、BAR 访问和 IRQ 等 vfio-user 协议操作；
Guest RAM 与 VRAM shared memory 则保存 QEMU 和 gem5 需要共同访问的大块内存数据。

### 5.1 控制面和数据面的直观图

```text
控制与通知
──────────
Guest Runtime/Driver
       │ BAR/MMIO/Doorbell
       ▼
QEMU vfio-user client ═════ Unix socket ═════► gem5 vfio-user server
       ▲                                           │
       └──────────────── MSI-X/IRQ 通知 ───────────┘

大块数据
────────
QEMU Guest RAM  ═════ /dev/shm/cosim-guest-ram-<run-id> ═════ gem5 DMA/GPUVM

QEMU BAR0/VRAM  ═════ /dev/shm/mi300x-vram-<run-id>      ═════ gem5 VRAM 模型
```

vfio-user 还负责 PCI region 协商，并能为适合 mmap 的 region 传递共享 backing。
因此“socket 负责控制，共享内存承载 bulk data”是职责划分，不表示两者在连接建立时
毫无关系。

这里的 backstore 可以先理解为“在外层 Host 上实际保存模拟内存字节的文件”。

### 5.2 三类通道各自装什么

| 通道                    | 主要内容                                                | 判别依据       |
| ----------------------- | ------------------------------------------------------- | -------------- |
| vfio-user socket        | PCI config、回调式 BAR 访问、Doorbell、MSI-X 等协议操作 | 设备控制或通知 |
| Guest RAM shared memory | Guest 物理内存，以及 gem5 DMA 可见的系统内存            | Guest RAM 内容 |
| VRAM shared memory      | BAR0/GPU VRAM backstore                                 | GPU VRAM 内容  |

Queue、页表、Kernel 参数、输入、输出和完成对象最终位于 Guest RAM 还是 VRAM，要由
实际分配与映射决定。Phase 1 只认识“控制通道”和“数据存放处”，不推导 CPU VA、
Guest PA、GPU VA 或 VRAM offset；这些留到 Phase 4。

### 5.3 BAR 布局

```text
vfio-user PCI GPU
│
├─ BAR0 + BAR1 ──► VRAM aperture ─────► VRAM shared memory
├─ BAR2 + BAR3 ──► Doorbell aperture ─► 通知 GPU 检查 Queue
├─ BAR4        ──► MSI-X table/PBA ───► 中断通知
└─ BAR5        ──► MMIO registers ────► 初始化与设备控制
```

BAR1 和 BAR3 是前一个 64-bit BAR pair 的高半部，不是额外的数据通道。本阶段也不解析
BAR 内 offset、寄存器位、Doorbell ID 或 MSI-X vector。

### 5.4 三个常见误区

1. **“A、B、C 都从 socket 一包包传给 gem5。”** 不对。大块内存内容位于 Guest
   RAM 或 VRAM shared backstore。
2. **“写 Doorbell 就说明 Kernel 已运行完成。”** 不对。Doorbell 只通知有新任务。
3. **“看见 shared memory 文件，就已经知道 GPU 地址转换。”** 不对。文件是
   backstore，GPUVA 到 backing offset 的路径属于 Phase 4。

## 6. 用一张图看完 `vector_add` 的五条数据流

下面不是五次不同运行，而是**同一次运行的五种观察角度**。

```text
[1 启动初始化]
wrapper → gem5 server 就绪 → QEMU/Guest 启动 → amdgpu/KFD → ROCm 发现 gfx942
                         │
                         ▼
[2 命令提交]
Guest HIP launch → Queue 中发布任务 → Doorbell ──socket──► gem5 Dispatch/CU
                         │                                  │
                         │                                  │
[3 内存数据]             ▼                                  ▼
代码 / Queue / 参数 / A、B、C / Signal ══ Guest RAM 或 VRAM shared memory ══
                                                            │
                                                            ▼
[4 完成返回]
Guest 应用继续执行 ◄─ Runtime 观察 Signal ◄─ 结果与完成状态 ◄─ gem5 Kernel complete
                              ▲
                              └─ polling，或经 IH/MSI-X 获得中断通知

[5 证据与资源]（贯穿以上所有步骤）
invocation → qemu.log → gem5-evidence.tsv → verdict.json → cleanup-status.txt
```

### 6.1 启动初始化

wrapper 创建 run 资源，gem5 先发布 PCI endpoint，QEMU 再启动 Guest 并连接它。
Guest 的 `cosim-gpu-setup.service` 发布 ROM/discovery 数据并加载
amdgpu，随后 KFD/ROCm 使 `gfx942` agent 可用。

这一段回答“设备何时可用”，不回答某个 amdgpu 函数怎样初始化 IP block；后者留到
Phase 3。

### 6.2 命令提交：任务正文和通知分开走

Runtime 复用初始化阶段已建立的 GPU 地址空间、Queue 和 Doorbell。它先把完整任务
发布到 Queue，再写 Doorbell。QEMU 把 BAR2 访问交给 gem5，GPU 命令模型取得任务、
建立 Dispatch 并把工作交给建模 CU。

Driver 负责建立和保护资源，但正常用户 Queue 热路径不等于每次 Launch 都重新创建
全部资源。Packet 字段、write index 和发布顺序留到 Phase 5。

### 6.3 内存数据：不是一条“复制箭头”

代码、Queue、页表、参数、A/B/C 和 Signal 都是内存对象。QEMU 与 gem5 通过 Guest
RAM/VRAM backstore 看到相关内容；对象究竟放在哪里、经过怎样的 GPUVM 转换，当前
阶段不做猜测。

### 6.4 完成返回：完成状态与通知不是同一件事

gem5 完成 Workgroup（本阶段先理解为一批逻辑工作）和 Kernel 后写回结果，并更新
完成状态。Runtime 可以主动轮询 Signal，也可以通过 IH/MSI-X 路径被唤醒。必须分开
三个事件：

```text
Kernel 已完成  ≠  Signal 已更新  ≠  Guest CPU 收到中断
```

Phase 1 只认识 polling 和 interrupt 两类路线，严格时序留到 Phase 6。

### 6.5 证据与资源：为前四条路径建立闭环

run ID 把输入身份、Guest 输出、gem5 执行事件、分类结果和清理结果串在一起。证据的
价值不是“日志很多”，而是每一份材料只回答一个明确问题：

```text
本次用了什么？       → invocation / provenance
Guest 程序正确吗？    → qemu.log / test exit code
GPU 模型执行了吗？    → gem5-evidence.tsv
为何判 PASS/FAIL？     → verdict.json
资源清理了吗？        → cleanup-status.txt
```

### 暂停检查 4

不用看图，尝试从“Guest 调用 HIP Kernel”讲到“应用读取 C”。讲述中至少要出现
Queue、Doorbell、vfio-user、gem5、shared memory、Signal，以及 Guest 结果、GPU
执行和清理三类证据。如果顺序卡住，回到本节总图，而不是先钻进源码。

## 7. 读取一次真实 PASS artifact

下面使用本机既有样本核对前面介绍的结构和数据流：

```text
artifacts/quick/quick-vector-add-20260826-225106/
```

该目录被 Git 忽略，是当前工作机上的学习样本，不是其他机器必然存在的仓库输入。

### 7.1 按证据层次阅读

```text
1. 输入身份
runner-metadata.txt / invocation / provenance
          │
          ▼
2. Guest 结果
qemu.log
          │
          ▼
3. GPU 模型执行
gem5-evidence.tsv / gem5.log
          │
          ▼
4. 综合判定与收尾
verdict.json / matrix.tsv / cleanup-status.txt
```

### 7.2 输入身份

`runner-metadata.txt` 中的关键行是：

```text
run_id=quick-vector-add-20260826-225106
program=vector_add
guest_test_prefix=HSA_ENABLE_INTERRUPT=0
gem5_config_args=defaults:num-gpus=1,num-cus=40,host-mem=8G,vram-size=16GiB;...
```

这四行建立了本次运行身份：单 GPU、40 个建模 CU、8 GiB Guest RAM、16 GiB VRAM，
并使用 polling 模式。它们还不能证明程序正确或 GPU 已经执行。

再用 `runner-invocation.txt`、`launch-invocation.txt`、
`patch/source-snapshot.txt` 和 `patch/binary-provenance.txt`
确认 runner 参数、QEMU/gem5/Guest 输入和源码/二进制身份。

### 7.3 Guest 程序结果

`qemu.log` 中可以看到：

```text
hipcc --offload-arch=gfx942 ... -o build/vector_add kernels/vector_add.cpp
[RUN] vector_add (timeout: 60s)
PASS: vector_add correctness
[PASS] vector_add
```

这证明 Guest 编译了 `gfx942` 目标，程序输出符合预期。但仅凭这一段，仍
不能排除“结果来自错误路径或 GPU 模型没有真正推进”的可能。

### 7.4 GPU 模型执行证据

`gem5-evidence.tsv` 是结构化事件，不必先在大段 `gem5.log` 中
盲搜。以下是同一 dispatch 的节选：

```text
seq  event                 dispatch  wg  cu
3    kernel_launch         0         -1  -1
4    workgroup_dispatch    0          0   0
10   workgroup_complete    0          0  -1
14   kernel_complete       0         -1  -1
```

它给出一条最小因果链：Kernel 被模型接收，Workgroup 被派发并完成，最后 Kernel
完成。整个测试边界内实际记录了 3 次 `kernel_launch` 和 23 次
`workgroup_dispatch/complete`；Phase 1 不猜测三个 Kernel 的具体身份，
单个 Packet 对应留到 Phase 5。

### 7.5 综合判定和资源收尾

`verdict.json` 的关键信息可以压缩为：

```json
{
  "outcome": "PASS",
  "reason": "all_acceptance_gates_passed",
  "compile": true,
  "gpu_execution": true,
  "cleanup": "verified"
}
```

这是便于学习的字段摘要，不是 `verdict.json` 的原始完整结构。
`matrix.tsv` 把程序、实际中断模式、run、结果和 artifact 路径汇总为一行；
`cleanup-status.txt` 则记录：

```text
result=PASS
primary_category=test_pass
secondary_category=none
```

### 7.6 三类成功证据缺一不可

```text
PASS 验收
├─ Guest 程序结果正确：qemu.log / test exit code
├─ GPU 模型确实执行：gem5-evidence.tsv
└─ 运行身份与资源收尾闭环：provenance / verdict / cleanup
```

- 只有 Guest PASS：不能证明 GPU 模型确实执行。
- 只有 `kernel_complete`：不能证明应用拿到了正确结果。
- 只有 cleanup verified：只能证明资源收尾，不能证明功能正确。

三类证据一致，才构成当前项目所说的 PASS。

假设别人只发给你一行 `[PASS] vector_add`，你还会索要哪两类证据？如果
能回答“结构化 GPU 执行事件”和“输入身份/综合判定/清理”，说明你已经开始按证据而
不是按印象理解项目。

## 8. 三层边界：这条结论能说到哪里

到这里已经知道系统怎样运行。最后要防止的是：把真实 AMD 软件、gem5 模型和 cosim
适配层混成“物理 MI300X 事实”。

### 8.1 三个标签的最短定义

```text
[REAL AMD]  Guest 中固定版本的 AMD Linux/ROCm 软件语义，以及通用 HSA 合同

[GEM5]      gem5 当前真正实现的 GPU 行为模型

[COSIM]     为 QEMU 与 gem5 协作而增加的 synthetic device、transport 和运行管理
```

同一条路径可以跨越三层：

```text
HIP/ROCr                    amdgpu/KFD
[REAL AMD] ───────────────► [REAL AMD，运行在 COSIM 条件下]
                                      │
                                      ▼
synthetic PCI / ROM / vfio-user / shared backstore
[COSIM]
                                      │
                                      ▼
AMDGPUDevice / GPUVM / Dispatch / CU / Interrupt model
[GEM5]
```

标签不是在评价“真假”，而是在限定证据的外推范围。

### 8.2 用具体例子判断边界

| 结论                                                | 标签            | 能说什么                   | 不能外推什么                            |
| --------------------------------------------------- | --------------- | -------------------------- | --------------------------------------- |
| ROCr 用 Queue/Signal 表达提交与完成                 | `[REAL AMD]`  | 固定软件栈和 HSA 语义      | 所有 GPU 代际内部实现完全一致           |
| amdgpu/KFD 在 Guest 中建立设备与进程资源            | `[REAL AMD]`  | 真实驱动职责               | 当前 endpoint 是完整物理 MI300X         |
| vfio-user、synthetic ROM/discovery、run ID、overlay | `[COSIM]`     | 当前协同仿真怎样连接和隔离 | 物理 MI300X 也有这些 wrapper/workaround |
| gem5 记录 Dispatch、Workgroup 和 Kernel complete    | `[GEM5]`      | 模型确实推进这些事件       | 芯片全部 IP、Firmware 和时序已完整建模  |
| `--num-cus=40`                                    | `[GEM5]` 配置 | 当前 run 使用 40 个建模 CU | 物理 MI300X 的 CU 数量或性能            |

### 8.3 外部知识怎样迁移

外部 RDNA 3/RX 7800 XT 材料可以帮助理解 Grid、Workgroup、Wave、Queue、Doorbell
和完成通知等通用概念，但不能直接把以下内容写成当前 `gfx942` cosim 事实：

- WGP/CU 组织和硬件数量；
- wave 模式；
- Firmware/MES 路径；
- cache、调度或性能特征。

真实 GPU 的 PSP、SMU、安全、电源、RAS 和多种 Firmware 控制域，也不能因为 Guest
驱动具有相应接口，就推导为当前模型已实现、已实测的热路径。
